# Loop IM 测试用例集

> 从**实际使用**的角度，把这个系统「一个人能做的每一件事」列成可执行的用例：
> 怎么测、期望什么、**为什么要测这一条**。既是发版前的回归清单，也是新功能的验收对照表。

最后更新：2026-08-27 · 对应代码：手机端顶栏保存按钮改走系统分享（可存相册）合入后

## 0. 为什么要有这份文档

现在仓库里**自动化用例并不少**，跑一遍全绿：

| 层 | 文件数 | 用例数 | 实测 |
| --- | --- | --- | --- |
| 后端 `server/test` | 58 | **940**（204 个 suite） | ✅ 全绿 · 13s |
| 前端 `web/src/**` | 78 | **930** | ✅ 全绿 · 8s |
| 端到端 `e2e` | 4 | **13** | ✅ 全绿 · 13s |
| 合计 | 140 | **1883** | 2026-08-26 实测 |

2026-08-21 另做了两轮针对**真实 Docker + MinIO 部署**的验证：
接口层 32 项（[§9](#9-真实环境验证记录2026-08-21)）、
真实浏览器 22 条（[§10](#10-浏览器验证记录2026-08-21)，已固化为 `e2e/deployed/`）。
2026-08-26 又对**线上生产环境**做了一轮 PWA 专项验证（[§11](#11-线上-pwa-验证记录2026-08-26)）。

但这些用例是按**模块和 issue 号**组织的（`issue-22.test.js`、`reactions.test.js`……）。
它回答的是「这段代码对不对」，回答不了下面这三个问题：

1. **发版前该点哪些地方？** —— 没有一份按人的操作路径串起来的清单。
2. **这个功能到底有没有人验过？** —— 比如「上传头像」「切换深色主题」「真实 MinIO 回源」，
   翻遍 95 个测试文件才能确认答案是「没有」。
3. **自动化覆盖不到的部分是哪些？** —— 真实浏览器通知、真实大模型调用、Docker 部署、
   老库升级，这些永远得靠人，但从来没被列出来过。

这份文档就是补这三件事。**用例以「使用者能感知的行为」为单位**，不以函数或文件为单位。

## 1. 怎么读

每条用例的字段：

| 字段 | 含义 |
| --- | --- |
| **编号** | `TC-<模块>-<序号>`，稳定不复用。删掉的用例编号作废，不给新用例。 |
| **场景** | 一句话说清「谁，在什么情况下，做了什么」。 |
| **步骤** | 可照着点的操作，用 `→` 串起来。 |
| **期望** | 使用者应该看到什么。写现象，不写实现。 |
| **目的** | **为什么要有这一条** —— 防的是哪一类回归。这一列比其他列都重要。 |
| **自动化** | 覆盖状态 + 对应文件。 |

自动化状态三档：

- ✅ **已覆盖** —— 有自动化用例守着，日常回归可以跳过手工，只在改动相关代码时抽查。
- ◐ **部分覆盖** —— 逻辑层有测试，但**使用者实际看到的那一层**没有（真实浏览器、真实网络、
  真实第三方）。发版前建议人工过一遍。
- ✋ **只能人工** —— 自动化测不了或成本不合理。**每次发版必须人工执行**，汇总见 §5。

## 2. 测试环境准备

### 2.1 起一套本地环境

```bash
cd server && cp .env.example .env
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # 填 JWT_SECRET
# 再填 ADMIN_EMAIL / ADMIN_PASSWORD

npm install --prefix server && npm install --prefix web
npm start --prefix server                    # http://localhost:4000
npm run dev --prefix web                     # http://localhost:5173
```

### 2.2 测试账号矩阵

大部分用例需要**同时有 4 个身份在场**，建议在 `.env` 里一次性造好：

```bash
DEMO_USERS=测试甲:jia@example.com:后端,测试乙:yi@example.com:前端,测试丙:bing@example.com:设计
DEMO_PASSWORD=test-only-password
```

| 代号 | 身份 | 用来验什么 |
| --- | --- | --- |
| **A** | 管理员（`ADMIN_EMAIL`） | 管理入口、建群、AI 配置、停用/重置密码 |
| **B** | 普通成员 测试甲 | 对端视角：收消息、已读回执、在线状态 |
| **C** | 普通成员 测试乙 | 第三方视角：群里的旁观者、非成员的越权尝试 |
| **D** | 普通成员 测试丙 | 被停用 / 被移除群 / 被重置密码的对象 |
| **Aria** | 系统 AI | AI 相关全部用例 |

> **浏览器要求**：A 用常规窗口，B 用另一个浏览器（不是隐私窗口——部分用例要验
> localStorage 持久化），C/D 用隐私窗口。同一浏览器的多个标签共享同一 token，
> 会互相影响，见 TC-AUTH-14。

### 2.3 三种运行模式

不少用例的期望值取决于当前模式，执行前先确认自己在哪一档：

| 模式 | 怎么进入 | 影响哪些用例 |
| --- | --- | --- |
| **① 默认（离线可跑）** | 不配 AI 凭据 | AI 走**本地模拟回复**，AI 全模块可测流程但不测质量 |
| **② 真实大模型** | AI 配置页填真实 Key | TC-AI-14~17 只能在这一档验；注意会**真实计费** |
| **③ 对象存储** | `.env` 填 `S3_BUCKET` 等 | TC-OPS-01~06 只能在这一档验；需要本地起 MinIO |

### 2.4 自动化命令

```bash
npm run test              # 后端 + 前端（约 1 分钟）
npm run test:server       # 940 条，跑在临时 SQLite 上，不碰 server/data
npm run test:web          # 930 条，vitest + jsdom
npm run test:e2e          # 先构建前端，再用 Playwright 跑 13 条真实浏览器用例
npm run typecheck         # 前端类型检查
npm run test:coverage     # 覆盖率（前后端分别输出）
```

对**跑起来的部署**（真实 Docker / 真实对象存储）另有两套验证，互补：

```bash
# ① 接口层：响应头、鉴权、限流边界这些浏览器里看不出来的
ADMIN_PASSWORD=... MEMBER_PASSWORD=... OUTSIDER_PASSWORD=... \
  ./scripts/verify-deployment.sh            # 默认打 127.0.0.1:4000，可用 BASE= 改

# ② 真实浏览器：图片到底渲染没有、PDF 会不会被打开、主题刷新后还在不在
BASE=http://127.0.0.1:4000 ADMIN_EMAIL=... ADMIN_PASSWORD=... \
  M1_EMAIL=... M1_PASSWORD=... M2_EMAIL=... M2_PASSWORD=... M3_EMAIL=... M3_PASSWORD=... \
  npm run test:deployed                     # 详见 e2e/deployed/README.md
```

两者都会往目标环境写数据，**只指向测试环境**。

## 4. 用例

### A. 登录与身份 `AUTH`

| 编号 | 场景 | 步骤 | 期望 | 目的 | 自动化 |
| --- | --- | --- | --- | --- | --- |
| TC-AUTH-01 | 正常登录 | 输入 A 的邮箱密码 → 登录 | 进入应用，右上角提示「已上线」，联系人里自己是在线 | 主路径，挂了什么都别测了 | ✅ `auth.test.js` · `smoke.spec.ts` |
| TC-AUTH-02 | 密码错误 | 故意输错密码 | 明确的失败提示，不透露「邮箱是否存在」 | 错误提示不能变成账号枚举工具 | ✅ `auth.test.js` |
| TC-AUTH-03 | 勾「保持登录」 | 勾选后登录 → 关标签页 → 重开 | 仍是登录态；凭据存在 localStorage，有效期 15 天 | 勾选框必须真的有用，不是装饰（issue #3 的回归） | ✅ `issue-3.test.js` · `lib/issue-3.test.ts` |
| TC-AUTH-04 | 不勾「保持登录」 | 不勾选登录 → 关标签页 → 重开 | 回到登录页；凭据在 sessionStorage，有效期 1 天 | 同上，反向 | ✅ `issue-3.test.js` |
| TC-AUTH-05 | 改密码踢掉其他设备 | B 在两处登录 → 在其一改密码 | 另一处下次操作即失效并跳登录页；改密码这一处继续可用 | 改密码的**意义**就是让泄露的旧凭据作废（issue #2） | ✅ `issue-2.test.js` |
| TC-AUTH-06 | 改密码不降级存储模式 | 不勾「保持登录」→ 改密码 | 换发后仍是「仅本次会话」，不会偷偷变成长期保存 | 合并期真实引入过的缺陷，必须钉死 | ✅ `lib/issue-3.test.ts` |
| TC-AUTH-07 | 凭据失效的文案归因 | 用升级前的老 token / 改过密码的旧 token 各访问一次 | 两种情况给**不同**的提示，不都说成「密码被改了」 | 误导性文案会让人以为账号被盗（issue #16） | ✅ `issue-16.test.js` |
| TC-AUTH-08 | 登录失败限流 | 同一邮箱连续输错 11 次 | 第 11 次起被拒，等窗口过去（默认 15 分钟）才恢复 | 挡暴力破解 | ✅ `hardening-v2.test.js` |
| TC-AUTH-09 | 限流只数失败 | 错 5 次 → 登录成功 → 再错 | 计数清零，不会因为之前错过就提前锁 | 限流不能误伤正常人 | ✅ `hardening-v2.test.js` |
| TC-AUTH-10 | 主动退出 | A 退出登录 | 回登录页；B 那边 A **立刻**变离线（不用等 90 秒心跳窗口） | 退出要真的下线，不是清个本地 token（issue #6） | ✅ `issue-6.test.js` · `issue-6.test.tsx` |
| TC-AUTH-11 | 退出时的在途请求 | 网络慢时点退出（可用 DevTools 限速） | 干净地回到登录页，**不弹未处理错误** | 退出竞态曾把页面打出错误（issue #21） | ✅ `issue-21.test.tsx` |
| TC-AUTH-12 | 心跳与在线判定 | B 登录后放着不动 | 每 45 秒心跳一次；断网超过 90 秒后别人看到 B 离线 | 在线状态是所有人第一眼看的信息 | ◐ `auth.test.js`（窗口逻辑）；真实断网 ✋ |
| TC-AUTH-13 | 生产缺密钥拒绝启动 | `NODE_ENV=production` 且不设 `JWT_SECRET` → 启动 | 直接拒绝启动并说明原因 | 绝不允许拿默认密钥裸奔上线 | ✅ `hardening.test.js` |
| TC-AUTH-14 | 同浏览器多标签 | 同一浏览器开两个标签 → 其一退出 | 两个标签一起失效 | **已知限制**，不是 bug；文档里承诺过，别当回归报 | ◐ `issue-6.test.js` |
| TC-AUTH-15 | 停用账号的登录 | A 停用 D → D 尝试登录 | 拒绝登录，提示账号已停用 | 离职即刻失效的第一道门 | ✅ `disable-user.test.js` |
| TC-AUTH-16 | 密码可见性切换 | 登录页密码框点小眼睛 | 明文/密文来回切；已输入的内容不丢；点它**不会**把表单提交出去 | 输错时能看一眼再交，少触发一次登录限流；切换按钮混成 submit 是最容易犯的实现错 | ✅ `password-toggle.test.tsx` |
